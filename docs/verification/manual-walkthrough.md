# 수동 검증 순서 — 한 번에 1~2개

자동 검증은 코드·프로토콜·집계까지 확인했다. 이 문서는 실제 VS Code 창에서 사람이 봐야 하는 항목을 **한 묶음에 1~2개**로 나눈 진행 순서다. 각 단계의 전체 서술은 단계별 체크리스트에 있고, 여기서는 바로 따라 할 수 있는 순서·명령·판정 기준만 적는다.

- 기준 브랜치: `feat/complete-view-contract`
- 관련 문서: [4단계](step4-manual-checklist.md), [5단계](step5-manual-checklist.md), [6단계](step6-manual-checklist.md), [7단계](step7-manual-checklist.md), [8단계 대체표](step8-replacement-table.md)
- 원칙: 자동 통과를 수동 통과로 바꾸지 않는다. 관찰하지 못한 항목은 `미확인`으로 남긴다.

## 0. 공통 준비 (한 번만)

1. 저장소를 최신 브랜치로 맞추고 빌드한다.

   ```bash
   cd /Users/sjh354/Documents/skein
   git switch feat/complete-view-contract
   git pull
   npm ci
   npm run build
   ```

2. VS Code에서 이 폴더를 열고 `F5`를 누른다. `Run Skein Extension` 설정이 `preLaunchTask: npm: build`로 빌드한 뒤 Extension Development Host 창을 연다.
3. 개발 호스트 창에서 검증용 워크스페이스를 연다.
   - 기본: 저장소의 `tests/fixtures` 폴더
   - 변경 기능(5·6단계): 복사한 임시 작업공간. 원본 저장소의 Git 상태를 건드리지 않는다.
4. Codex MCP 등록(이미 있으면 생략).

   ```bash
   codex mcp add skein --env WORKSPACE_ROOT=/Users/sjh354/Documents/skein -- node /Users/sjh354/Documents/skein/dist/mcpServer.mjs
   ```

5. 결과 기록은 아래 형식으로 묶음마다 남긴다.

   ```text
   묶음: 4단계 M1·M2
   날짜/커밋:
   통과: 예 / 아니오 / 일부
   관찰: (화면에서 본 것, 걸린 시간, 거부 메시지 원문)
   문제 재현 절차:
   ```

> 그래프 탭이 안 보이면 명령 팔레트에서 `Skein: Focus Graph View`를 실행한다. 첫 실행은 인덱싱 때문에 몇 초 걸릴 수 있다.

## 1. 4단계 M1·M2 — 선택과 포커스

목표: 마우스 선택과 MCP `select`/`focus`가 같은 화면을 움직이는지 본다.

1. TS 파일을 열고 함수 안에 커서를 둔 뒤 `Skein: Show Call Graph`를 실행한다.
2. 그래프에서 아무 노드나 클릭한다. 노드가 선택 표시되고 상세 패널이 그 노드로 바뀌는지 본다.
3. `skein_get_view_state`로 현재 `selection.nodeId`를 확인한다.
4. Codex에 그 값을 그대로 넘겨 `skein_control_view`의 `select`를 실행한다. 하이라이트와 상세 패널이 같은 노드로 유지되는지 본다.
5. 그래프를 드래그·축소해 대상 노드를 화면 밖으로 보낸 뒤, 같은 노드에 `focus`를 실행한다. 뷰포트가 실제로 이동·확대되는지 본다.
6. 존재하지 않는 ID로 `select`를 실행해 `node-not-found` 거부가 오고 화면이 그대로인지 확인한다.

통과 기준:

- [ ] 클릭 선택과 `select`가 같은 상세 패널을 연다.
- [ ] `focus`가 선택만 바꾸지 않고 뷰포트를 움직인다.
- [ ] 없는 노드는 거부되고 화면이 변하지 않는다.

## 2. 4단계 M3·M4 — 필터와 펼침

1. 파일 그래프에서 노드 타입 필터 하나를 켠다(예: 폴더 숨김). 캔버스에서 실제로 사라지는지 본다.
2. `skein_control_view`의 `set_filter`로 같은 필터를 켜고 끈다. MCP 응답의 `applied`와 화면이 일치하는지 본다.
3. `set_expand_all`로 의존성 그래프를 펼치고 접는다.
4. 파일 그래프의 노드 하나를 골라 `set_expanded`로 그 노드만 펼친다. 다른 노드는 그대로인지 본다.
5. 아키텍처 뷰에서 그룹 하나만 `set_expanded`로 펼치고 접는다. `unit` 노드에 보내면 `unsupported-node-kind`로 거부되는지 확인한다.

통과 기준:

- [ ] `set_filter`가 캔버스의 노드·엣지를 실제로 숨기고 해제한다.
- [ ] 전체 펼침과 개별 펼침이 서로를 덮어쓰지 않는다.
- [ ] 지원하지 않는 대상은 명시적으로 거부된다.

## 3. 4단계 M5·M6 — 재시작 복원과 실제 클릭 우선

1. 콜 그래프에서 노드를 몇 개 옮기고 줌·팬을 바꾼 뒤 창을 닫았다가 다시 연다. 배치가 눈으로 같은 위치에 복원되는지 본다.
2. `.skein/state.json`의 `layout`·`graphVersion`이 재시작 뒤에도 이어지는지 확인한다.
3. 긴 `timeoutMs`로 대기 중인 명령을 보낸 뒤, 그 사이 그래프를 실제로 클릭한다. 명령이 `user-action-superseded`로 거부되는지 본다.

통과 기준:

- [ ] 재시작 후 노드 위치·줌·팬이 유지된다.
- [ ] 사용자가 먼저 조작하면 대기 명령이 화면을 덮지 않는다.

## 4. 4단계 M7·M8 — 멀티루트와 Codex 왕복

1. 멀티루트 워크스페이스에서 `skein.setWorkspace`로 영역을 바꾼다. `state.json`의 대상 루트가 바뀌는지 본다.
2. 같은 폴더를 창 두 개로 열고 `windows`·`activeWindowId`가 분리되는지 확인한다. 한 창에 보낸 명령이 다른 창을 바꾸지 않는지 본다.
3. Codex에서 `get_view_state`가 준 `nodeId`·`filePath`·`windowId`를 가공 없이 `control_view`에 넘긴다. 응답과 화면이 일치하는지 본다.

통과 기준:

- [ ] 창별 상태가 섞이지 않는다.
- [ ] MCP가 돌려준 식별자를 그대로 다시 써도 동작한다.

## 5. 4단계 M9·M10 — 미리보기와 모든 뷰의 계약

1. `open_file`로 파일을 연다. 미리보기 탭으로 열리는 동작이 작업 흐름에 불편하지 않은지 본다.
2. 파일·리스트·심벌·아키텍처 뷰를 차례로 열고 각각 노드를 클릭한다. `state.json`의 `views[mode]`가 그 뷰의 선택으로 갱신되는지 본다.
3. 각 뷰에서 `search`를 실행한다. 현재 렌더러가 로드한 노드 중 첫 일치로 포커스가 가는지 본다. 전체 프로젝트 검색은 `skein_graph_context`의 검색 모드를 쓴다.
4. 아키텍처 뷰에서 `set_architecture`로 `view`(graph/matrix)·`unit`·`folder`·`minImports`를 한 단계씩 바꾼다. 한 호출에 한 단계만 바뀌는지 본다.
5. `state.json`의 `surface`에서 노드 ID·펼침·검색·분석 개수·아키텍처 revision·진단 참조가 보이는지 확인한다. 상세 근거는 `skein_diagnose_structure`로 조회한다.

통과 기준:

- [ ] `views[mode]`가 뷰별로 따로 저장된다.
- [ ] `search`는 로드된 범위에서 동작하고 그 한계가 응답에 드러난다.
- [ ] `set_architecture`가 한 번에 한 단계만 움직인다.
- [ ] `surface`만으로 화면 상태를 요약할 수 있고, 상세는 기존 도구로 조회된다.

## 6. 5단계 M1·M3 — 이름 변경 UI와 저장 전 편집

1. 편집기에서 심벌 이름을 바꾸는 계획을 만든다. 미리보기 diff와 확인 모달을 본다.
2. 적용한 뒤 Undo/Redo가 파일과 이력을 함께 되돌리는지 본다.
3. 파일을 저장하지 않고 수정한 상태에서 이름 변경을 시도한다. 저장 전 편집이 있다는 이유로 거부되고, 편집 내용이 보존되는지 본다.

통과 기준:

- [ ] 미리보기와 실제 적용 결과가 같다.
- [ ] 저장하지 않은 편집을 임의로 덮지 않는다.

## 7. 5단계 M4·M5 — 충돌과 이력 화면

1. 이력 화면에서 이전 계획과 현재 파일을 비교한다.
2. 파일을 밖에서 바꿔 충돌을 만든다. 충돌 hunk가 표시되고 해결 선택지가 나오는지 본다.
3. 해결 후 이력 항목이 실제 결과와 맞는지 확인한다.

통과 기준:

- [ ] 충돌이 숨겨지지 않고 hunk 단위로 보인다.
- [ ] 해결 결과가 이력에 정확히 남는다.

## 8. 5단계 M6·M7 — 멀티루트와 Codex 호출

1. 5단계 6번(M6)에 따라 영역을 바꿔도 계획·이력이 섞이지 않는지 본다.
2. Codex에서 이름 변경 도구를 실제로 호출한다. 계획·미리보기·적용 응답이 UI와 같은지 본다.

통과 기준:

- [ ] 영역 전환 뒤에도 대상 파일이 정확하다.
- [ ] Codex 응답과 UI 이력이 일치한다.

## 9. 5단계 M8·M9 — Git 격리와 중단 복구

1. 변경 적용 전후로 `git status`·`git diff`·현재 브랜치·인덱스를 확인한다. 사용자의 Git 상태가 바뀌지 않아야 한다.
2. 적용 도중 프로세스를 강제 종료한다. 다시 열었을 때 중단된 작업이 복구되거나 안전하게 정리되는지 본다.

통과 기준:

- [ ] 사용자 Git HEAD·인덱스·브랜치가 그대로다.
- [ ] 강제 종료 뒤 반쯤 적용된 파일이 남지 않는다.

## 10. 5단계 M2·M10 — Dart 이름 변경과 실패 처리

1. Dart 확장이 있는 환경에서 Dart 심벌 이름을 바꾼다. 미리보기와 적용이 동작하는지 본다. 확장이 없으면 그 사실을 기록하고 건너뛴다.
2. 검증이 실패하는 변경을 시도한다. 실패 사유가 화면에 남고 파일이 부분 적용되지 않는지 본다.

통과 기준:

- [ ] 지원 환경이면 Dart도 같은 흐름으로 동작한다.
- [ ] 실패가 조용히 성공으로 표시되지 않는다.

## 11. 6단계 M1·M2 — 이동 (새 파일·기존 파일)

1. 새 파일로 심벌을 이동한다. 생성·삭제가 한 계획으로 보이는지, 적용 후 import가 맞는지 본다.
2. 기존 파일·공유 helper로 이동한다. 이름 충돌·재수출이 있으면 차단 사유가 보이는지 본다.

통과 기준:

- [ ] 이동 계획에 생성·삭제·import 수정이 모두 포함된다.
- [ ] 차단 사유가 구체적이다.

## 12. 6단계 M3·M7 — 차단 사유와 Undo/Redo

1. 진입점·이름 충돌·경로 별칭·재수출 상황을 각각 만들어 이동을 시도한다. 각 차단 사유가 구분되는지 본다.
2. 이동 적용 → Undo → Redo를 실행한다. 이후 편집이 보존되는지 본다.

통과 기준:

- [ ] 차단 사유가 상황별로 다르게 표시된다.
- [ ] Undo/Redo가 이후 편집을 잃지 않는다.

## 13. 6단계 M5·M6 — 추출과 인라인

1. 선택한 코드를 새 함수로 추출한다. 미리보기와 적용 결과를 본다.
2. 추출한 함수를 다시 인라인한다. 원래 코드와 의미가 같은지 본다.
3. 실패하는 추출·인라인을 시도해 사유가 표시되는지 본다.

통과 기준:

- [ ] 추출·인라인이 왕복해도 동작이 같다.
- [ ] 실패 사유가 화면에 남는다.

## 14. 6단계 M4·M8 — Dart 이동과 Codex 왕복

1. Dart 환경에서 실제 이동·private helper 이동을 실행한다.
2. Codex에서 `kind`: `move`/`extract`/`inline`으로 호출해 UI와 같은 계획·결과가 나오는지 본다.

통과 기준:

- [ ] Dart 환경이면 이동이 동작한다.
- [ ] Codex 응답이 UI 이력과 일치한다.

## 15. 6단계 M9 — 실제 프로젝트

2. 프로젝트 고유 설정(경로 별칭·재수출·생성 코드)에서 차단·허용이 합리적인지 본다.

통과 기준:

## 16. 7단계 M1·M2 — 프로필 위반과 예외

통과 기준:

- [ ] 예외 만료 후 위반이 다시 나타난다.

1. 규칙 위반을 만드는 변경을 시도한다. 적용 전에 차단되고 예외·사후 검증 흐름이 나오는지 본다.

## 20. 8단계 — 패널·에디터 동등성과 대체 화면

1. 하단 패널 그래프와 에디터 탭 그래프를 동시에 연다.
2. 한쪽에서 노드를 선택·펼침하고 호출 그래프 배치·줌·팬을 바꾼다. 다른 쪽에 반영되는지 본다.
3. 패널과 에디터의 캔버스 크기가 다를 때 줌·팬 보고가 섞여 화면이 튀지 않는지 본다.
4. 나중에 연 화면에 최근 분석 결과가 다시 전달되는지 본다.
5. 삭제한 렌더러·모듈 대신 현재 화면이 같은 기능을 제공하는지 [대체표](step8-replacement-table.md)를 보며 확인한다.
6. `skein.toggleViewMode`가 명령 팔레트에 없고, `setViewMode{File,List,Symbol,Architecture}`와 툴바로 전환되는지 본다.

통과 기준:

- [ ] 두 화면이 같은 분석 세션·선택·펼침을 공유한다.
- [ ] 뷰포트는 화면별로 분리되어 화면이 튀지 않는다.
- [ ] 제거한 명령이 남아 있지 않다.

## 진행 기록

### 2026-11-04 — 4단계 M1·M2·M5·M6 통과, M3·M4 결함 기록

- M1 통과: 클릭 선택과 `select`가 같은 상세 패널을 열고, 없는 노드는 `node-not-found`로 거부되며 화면이 유지됐다.
- M2 수정 후 통과: `focus`가 그래프를 다시 질의해 루트만 바꾸던 문제를 렌더러 surface `focus` 라우팅으로 수정. 뷰포트 이동·확대를 확인했다.
- M3 실패: `set_filter`는 `applied`·`hiddenFilters`만 남고 캔버스·범례는 그대로였다. 범례에서 Function·폴더·Incoming call을 꺼도 상태 게시가 바뀌지 않았다.
- M4 부분 통과: `set_expand_all true/false`의 펼침·접힘은 실제 반영됐다. 다만 `true` 뒤 로딩 오버레이가 접기 전까지 남았고, `expandedNodeIds`와 응답 `state`가 화면보다 한 박자 늦었다.
- M5 수정 후 통과: 재시작 뒤 노드 배치·줌·팬이 이전 화면과 같은 위치로 복원됐다.
- M6 통과: 드래그 중 보낸 `set_depth`가 `user-action-superseded`로 거부되고 조작·뷰포트가 유지됐다. 상세는 [4단계 체크리스트](step4-manual-checklist.md)의 D6~D10과 기록 표에 있다.
